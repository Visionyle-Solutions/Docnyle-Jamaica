# DocNyle — OPD Consultation Module
## API Integration Guide: Removing Static Data from the Web Forms App

**Document version:** 1.2 — October 2026
**Scope:** The **client side** of Phase 4 — where static (in-memory and hard-coded) data lives
in `OpdProject` today, and how to replace each piece with calls to the `DOCNyleUnifiedAPI` WCF
service, file by file, until `Services/DataStore.cs` can be deleted.
**Audience:** Engineers switching the Web Forms site from `DataStore` to the service.
**Companion documents:** `WCF-MIGRATION-GUIDE.md` (the **service side**: building
`DOCNyleUnifiedAPI`, its DAL, the database, phase gates P0–P6), `API-SPECIFICATION.md` v3.3 (the

> **Read this with `WCF-MIGRATION-GUIDE.md`, not instead of it.** That guide builds the service
> and owns the phase gates. This guide is the work list for `opd-project/` during P1 (auth) and
> P3–P6 (facade switch → decommission). Where they overlap (§9 of that guide), this guide is the
> more detailed one; where they differ, §6 below says why.

## 1. Summary — What "static data" means here

The app has **no database connection**. Every screen's data comes from one of four places:

| # | Kind | Where | Fate |
|---|---|---|---|
| A | **In-memory tables + seed** | `Services/DataStore.cs` (≈ 65 `List<T>` tables, `Seed()`), started by `Global.asax.cs:14` | **Delete** at the end (P6); the seed becomes `db/Scripts/0005_SeedDemoData.sql` |
| B | **Facade bodies that read/write those tables** | the 12 `Services/*Service.cs` classes that use `DataStore` (≈ 600 references) | **Rewrite** each body to call the service; keep the method signatures |
| C | **Code that bypasses the facade or relies on in-memory behavior** | `settings-hub.aspx.cs`, `BasePage.HospitalId`, `AppSession.CurrentUser`, demo passwords, in-process counters | **Fix** individually (§2.3) |
| D | **Hard-coded reference lists that have a table** | time zones, vital ranges, roles/features, … | **Replace** with the matching `List…` operation (§2.4) |

Everything else that *looks* static — enum dropdowns, UI step lists, unit conversion,
formatting — is presentation and **stays** (§3).

The pages themselves (`templates/**`, 242 facade call sites) are **not rewritten**: they keep
calling `PatientService.Get(...)`, `ConsultationService.SaveVitals(...)` and so on. Only what
happens *inside* those methods changes.

```
TODAY                                          AFTER
templates/**  ──►  Services/XService.Method()  templates/**  ──►  Services/XService.Method()
                     │                                              │
                     ▼                                              ▼
                   DataStore.List<T>                              Web/DocNyle.Call(api => api.Op(...))
                   (seeded in memory)                               │  SOAP + SessionToken header
                                                                    ▼
                                                                  DOCNyleUnifiedAPI.svc → SQL Server
```

## 2. Where the static data is — the inventory

Paths are relative to `opd-project/`.

### 2.1 (A) The in-memory store — `Services/DataStore.cs`

| Lines | What | Replace with |
|---|---|---|
| 17–29 | `Sync` lock and `NextId(prefix)` (`PAT-1001`, `INV-1002`, …) | Nothing. Ids are generated by SQL (`NEWSEQUENTIALID()`) and come back in each `Create…` result. MRNs, invoice and receipt numbers are generated by the procedures from `MRN_FORMAT` / `InvoicePrefix` / `ReceiptPrefix` |
| 31–104 | One `List<T>` per table (`Hospitals`, `Users`, `Patients`, `Consultations`, `Invoices`, …), plus `Permissions`, `WhatsAppConfig`, `EmailConfig`, `ConsultFormPublished/Drafts` | The SQL tables in `schema.sql`, reached only through operations |

## 3. What stays static (do not remove)

Removing these would add round trips and gain nothing. They are UI vocabulary, and most are
pinned by a `CHECK` constraint in `schema.sql`, so the database would reject any other value.

| Kind | Examples |
|---|---|
| Enum dropdowns in `.aspx` / `.ascx` (`<asp:ListItem>`) | gender, title, blood group, marital status (`patient-form.ascx`); allergy type/severity/status (`patient-allergies-form.ascx`); laterality, acute/chronic (`consultation-diagnosis-card.ascx`); routine/urgent (`consultation-referral.ascx`); lab/imaging (`consultation-labs.ascx`); result flags (`lab-portal.aspx`); coverage relation/mode/status (`coverage-form.ascx`); invoice and message status filters; addendum reasons (`consultation-360.aspx`); smoking/alcohol/activity/diet (`patient-family-social-tab.ascx`); frequencies (`patient-medications-tab.ascx`) |
| Placeholder items added in code-behind | `"— Select —"`, `"All Doctors"`, `"MM"` / `"YYYY"` |
| Page structure | `Steps` (`consultation-360.aspx.cs:52`), `Tabs` (`settings-hub.aspx.cs:20`, `schedule-settings.aspx.cs:31`, `Web/HealthRecord.cs:11`), `OnboardingSteps`, `KindTitles`, `PeriodTitles`, `StatusColors`, `Months`, `DayLabels` |
| Rules the UI needs before it calls the service | `SchedulingService.Transitions` / `StatusLabels` (which buttons to show — the service enforces the same transitions and returns a `Conflict` fault), `DayCodes`, `WeekDays`, `DoctorOverridable`, `InventoryService.Categories`, `ExportService.PatientRequiredColumns`, `LabService.FileTypes`, `ConsultationConfigService.InputTypes` / `SectionIcons` |
| Pure logic (`WCF-MIGRATION-GUIDE.md` §8) | `ClinicalEngines.cs`, `VitalUnitService`, `PhoneService`, `TimeZoneService` conversions, `HospitalService.FormatDate/FormatTime/FormatMrn`, `SchedulingService.RenderDoctorName`, `ServiceItemLabel`, `CoverageLabel`, `ComplianceLine` |
| Browser scripts | `js/site.js`, `js/engines/engine-voice-soap.js`, `js/components/component-drawing-pad.js` |

Rule of thumb: **if the value set is fixed by the product or the schema, keep it in code; if a
hospital can add, rename or disable rows, it comes from an operation.**

## 4. Target pattern — how a page gets data after the switch

### 4.1 The four new pieces in `OpdProject`

| File | Purpose |
|---|---|
| Connected Services → `DocNyleApi` | Generated client `DocNyleApi.DOCNyleUnifiedAPIClient` + data contracts (namespace `DocNyleApi`, collection type `List`). Spec §0.9 |
| `Web/DocNyle.cs` | The **only** code that creates the client: adds `SessionToken`, `ClientIp`, `ClientUserAgent`, `CorrelationId` headers; `Close()` / `Abort()`. Spec §0.9 |
| `Web/DataSource.cs` | Reads `DataSource:{Module}` from `Web.config` (`InProc` / `Wcf`) |
| `Services/Mapping/*Map.cs` | One static mapper per module: `DocNyleApi.Patient` → `Models.Patient`, request builders the other way. Keeps pages bound to `Models/*.cs` during the migration |

```csharp
// Web/DataSource.cs
public static class DataSource
{
    public static bool IsWcf(string module)
    {
        return string.Equals(ConfigurationManager.AppSettings["DataSource:" + module], "Wcf", StringComparison.OrdinalIgnoreCase);
    }

    public static bool AnyInProc
    {
        get { return Modules.Any(m => !IsWcf(m)); }
    }

    public static readonly string[] Modules =
        { "Users", "Hospital", "Patients", "Scheduling", "Consultation", "Catalog", "Lab", "Inventory", "Billing", "Operations", "ConsultationConfig", "UserNotifications" };
}
```

### 4.2 The facade method, before and after

**Read — one record**

```csharp
// BEFORE  Services/PatientService.cs
public static Patient Get(string patientId)
{
    lock (DataStore.Sync) return DataStore.Patients.FirstOrDefault(p => p.PatientId == patientId);
}

// AFTER
public static Patient Get(string patientId)
{
    if (DataSource.IsWcf("Patients"))
        return RequestCache.Get("Patient:" + patientId,
            () => PatientMap.ToModel(DocNyle.Call(api => api.GetPatient(patientId))));
    lock (DataStore.Sync) return DataStore.Patients.FirstOrDefault(p => p.PatientId == patientId);
}
```

`GetPatient` raises a `NotFound` fault for an unknown id; the facade turns that into `null`
when the pages expect `null` (they do for `Get`), so page code does not change:

```csharp
// Web/DocNyle.cs
public static T CallOrNull<T>(Func<DocNyleApi.DOCNyleUnifiedAPIClient, T> call) where T : class
{
    try { return Call(call); }
    catch (FaultException<DocNyleApi.ServiceFault> f) when (f.Detail.Code == DocNyleApi.FaultCode.NotFound) { return null; }
}
```

**Read — list / search.** Drop the LINQ filtering and sorting: the procedure already filters by
hospital, applies `IsActive`, and sorts. Never fetch a whole table and filter in C#.

```csharp
// BEFORE
lock (DataStore.Sync)
    return DataStore.Patients.Where(p => p.HospitalId == hid && (p.FullName.Contains(term) || p.Phone.Contains(term)))
                             .OrderBy(p => p.FullName).ToList();
// AFTER  — hid is no longer sent: the service takes the hospital from the session
return DocNyle.Call(api => api.SearchPatients(term)).Select(PatientMap.ToModel).ToList();
```

**Write — create.** No `NextId`, no `CreatedAt = DateTime.UtcNow`, no `CreatedBy`: the service
fills them. Return the row the service sends back so the page sees the real id / MRN.

```csharp
// BEFORE
p.PatientId = DataStore.NextId("PAT"); p.Mrn = NextMrn(hid); p.CreatedAt = DateTime.UtcNow;
lock (DataStore.Sync) DataStore.Patients.Add(p);
return p;
// AFTER
return PatientMap.ToModel(DocNyle.Call(api => api.CreatePatient(PatientMap.ToCreateRequest(p))));
```

**Write — update / toggle.** Send the change explicitly; never rely on having mutated a returned
object (§2.3). Toggles map to the operation that toggles or sets state:

```csharp
// BEFORE  UserService.ToggleActive
lock (DataStore.Sync) { var u = GetUser(id); u.IsActive = !u.IsActive; }
// AFTER
DocNyle.Call(api => api.UpdateUserActive(id));
```

**Multi-step writes.** Where the facade did several `DataStore` edits in one method (sign-off +
stock consumption, invoice generation, symptom cycle), the procedure usually does it all — see
`WCF-MIGRATION-GUIDE.md` §5.2–5.5 for `CycleSymptom`, `CreatePrescription`, `ConfirmSignOff`.
Remove the extra facade calls the page or facade made (e.g. `InventoryService.ConsumeForConsultation`
after `SignOff`).

**Cross-module reads.** Inside a facade, replace `DataStore.OtherTable` with the *other module's
facade method* (`ConsultationService.Get(id)`, not `DataStore.Consultations`). Do this **before**
switching any module — it is what makes the module-by-module toggle safe (§6).

### 4.3 Things that disappear from facade bodies

| Remove | Because |
|---|---|
| `lock (DataStore.Sync)` | SQL handles concurrency; the service is `PerCall` |
| `hospitalId` / `hid` parameters passed to the service | Tenant comes from the session (spec §0.4). Keep the facade **parameter** for now so pages compile; ignore it in the `Wcf` branch; remove it in P6 |
| `createdBy`, `userId`, `doctorId` "actor" arguments | Filled from the caller (spec §0.4). A doctor can only act as themselves |
| `DateTime.Now` / `TimeZoneService.Today(hid)` defaults sent as data | The service uses the hospital's today (`CallerContext.HospitalToday`) |
| Uniqueness checks (`EmailInUse`, `BrandExists`, `ItemCodeExists`) before a create | The procedure enforces the unique key and returns a `Validation`/`Conflict` fault; keep the facade method only if a page shows the error before submit, implemented by catching the fault |
| `BasePage.Audit(...)` calls that duplicate an **Audited** operation | The operation writes its own audit entry (spec §0.7). Keep page audits only for events with no operation (print, export download) |

### 4.4 Errors and round trips

- `BasePage` catches `FaultException<DocNyleApi.ServiceFault>` (`WCF-MIGRATION-GUIDE.md` §9.4):
  `Validation` / `BusinessRule` → `ToastDanger(Detail.Message)` and stay on the form;
  `NotFound` → error state; `Forbidden` → `access-denied`; `Unauthenticated` → sign out and
  redirect to login; `Internal` → generic message with the reference.
- Every facade call is now a network call. Add `Web/RequestCache.cs` (values in
  `HttpContext.Items`, per request) and `Web/HospitalCache.cs` (`MemoryCache`, per hospital,
  5 minutes) for reference data: `GetHospital`, `GetHospitalSettings`, `ListSpecialties`,
  `ListVitalsConfig`, `ListAppointmentTypes`, `ListPaymentMethods`, `GetPermissionMatrix`,
  `ListUsers` (for `UserName` lookups). **Clear the hospital cache in the facade's own save
  method** (`SaveSettings`, `CreateSpecialty`, …). Never cache patient data across requests.
- Measure `consultation-360.aspx`, `billing-checkout.aspx`, `settings-hub.aspx` and
  `patient-today-list.aspx` before and after; budget ≤ 15 calls per page load.

## 5. Step-by-step migration

Each step is one pull request or a small series. Steps 0–2 happen in **P1** of
`WCF-MIGRATION-GUIDE.md`; steps 3–6 are **P3**; step 7 is **P6**.

### Step 0 — Prerequisites

- `DOCNyleUnifiedAPI` runs locally (`https://localhost:44395/DOCNyleUnifiedAPI.svc`) against a
  database built by the DbMigrator with reference **and** demo seed.
- The demo seed keeps the same logins and patients as `DataStore.Seed()`, so
  `testing-guide.md` works on both.

### Step 1 — Infrastructure (no behavior change)

1. Add the service reference (`DocNyleApi`, collection type `List`).
2. Add `Web/DocNyle.cs`, `Web/DataSource.cs`, `Web/RequestCache.cs`, `Web/HospitalCache.cs`.
3. Add every `DataSource:{Module}` key to `Web.config`, all `InProc`; add `PortalHospitalId` and
   `ShowDemoLogins` (§2.3).
4. `BasePage`: fault handling (§4.4).
5. `Global.asax.cs:14`: `if (DataSource.AnyInProc) DataStore.Seed();`

Exit: app behaves exactly as today with all modules `InProc`.

### Step 2 — Authentication and session (module `Users`)

1. `login.aspx.cs` → `UserService.Authenticate` → `AuthenticateUser`; on success generate a
   256-bit token and call `CreateUserSession`.
2. `AppSession.SignIn(user, token)` stores the `AuthenticatedUser` and `ServiceToken`;
   `CurrentUser` returns the stored user after a cached `CheckSessionValid` (§2.3);
   `SignOut` clears both.
3. `UserService.HasPermission` reads the cached `GetPermissionMatrix` grid; `Navigation.cs` and
   `BasePage` keep calling it unchanged.
4. Remove the `demo123` defaults; hide demo logins behind `ShowDemoLogins`.

Exit: sign-in, sign-out, session timeout, access-denied and the sidebar work against the service
for every seeded role (`testing-guide.md` sign-in section).

### Step 3 — Untangle cross-module reads (still all `InProc`)

In every facade, replace reads of another module's `DataStore` tables with that module's facade
method (the "reads from other modules" column in §2.2). The biggest ones:
`OperationsService` (reports read 10 tables), `SchedulingService` (Patients, Users),
`BillingService` (Consultations), `LabService` (Orders, Patients), `InventoryService`
(ConsultationServiceItems), `CatalogService` (Diagnoses).

Reports (`ReportService.ConsultationVolume`, `DiagnosisFrequency`, `Prescribing`,
`AppointmentStatus`, `Revenue`) do **not** get rewritten as joins over other facades — they map
directly to the report operations (`ListConsultationVolumeReport`, …) when Operations switches.

Exit: `grep -n "DataStore\." Services/XService.cs` shows only tables X owns.

### Step 4 — Switch modules, owners first (§6)

For each module, in the order of §6:

1. Write the `Wcf` branch of every facade method using §7's map; add the mapper.
2. Fix that module's bypasses from §2.3 and hard-coded lists from §2.4.
3. Remove duplicated page `Audit(...)` calls.
4. Set `DataSource:{Module}` to `Wcf` in your environment; run that module's
   `testing-guide.md` section and the parity tests (`WCF-MIGRATION-GUIDE.md` §12).

## 6. Cut-over order and the mixed-store problem

`WCF-MIGRATION-GUIDE.md` §9.2 switches one module at a time. That only works if two rules hold,
because while some modules are `Wcf` the app has **two stores**: SQL and `DataStore`.

1. **Cross-module reads go through facades** (Step 3). Otherwise an `InProc` module reads a
   stale `DataStore` copy of a table the `Wcf` module now writes to SQL (e.g. a patient
   registered through the service is invisible to `InProc` scheduling).
2. **Owners switch before dependents.** A `Wcf` module that writes rows referencing another
   module's ids (an appointment's `PatientId`) needs those rows in SQL — the foreign keys reject
   ids that exist only in `DataStore`.

Order, derived from §2.2:

| Wave | Modules (`DataSource:` keys) | Depends on |
|---|---|---|
| 1 | `Users`, `Hospital` | — |
| 2 | `Patients` | 1 |
| 3 | `Scheduling` | 1, 2 |
| 4 | `Consultation`, `Catalog`, `Lab`, `Inventory` — **switch together** (Consultation ↔ Catalog share Diagnoses; Inventory consumes ConsultationServiceItems at sign-off; Lab reads Orders) | 1–3 |
| 5 | `Billing` | 1–4 |
| 6 | `Operations` (reports, message templates/queue, export, audit log reads) | all |
| 4 (with Consultation) | `ConsultationConfig` (custom values belong to consultations; publish updates `cfg.VitalDefinition`) and `UserNotifications` (created by `SubmitLabResult`) | 1–3 |

**Seed data in mixed mode.** While waves are split, `InProc` modules still hold *seed* rows that
point at seed ids (`PAT-001`), while SQL holds the same patients under GUIDs. Do mixed-mode
testing with **records created through the UI after the switch**, not the seeded history; test
the seeded scenarios only once the whole chain they touch is `Wcf`. In staging and production
there is no mixed mode — every key is `Wcf` (Step 6).
